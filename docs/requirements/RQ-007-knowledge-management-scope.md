# RQ-007：知识内容按业务团队管理的权限升级方案

状态：方案草案，尚未实现。日期：2026-10-22。

开发前提：系统仍处于开发阶段，本次直接采用目标表结构与接口契约，不要求向下兼容。后端、前端、Starter 及相关组件统一更新，不保留旧接口适配、双版本逻辑或兼容开关。

## 1. 目标与范围

不同业务团队在同一租户内维护知识，管理端应按本人、部门及数据控制组展示其负责的内容；已发布知识继续供租户内业务检索、问答和引用使用。

**产品边界（正式口径，非过渡态）：** 管理责任绑定创建者——知识由谁写入，即由谁（及其部门/授权控制组）在管理端维护。本期交付的是管理端**查看范围**，用于隔离各团队正在维护的内容；不是知识保密模型。业务上不存在、也不支持跨团队代管写入，**本期不引入跨团队写防护**。编辑、删除、审核、发布、回滚等命令维持既有规则，不新增写权限判断；若后续要求部门负责人代改下属知识等，另行升级写权限。

| 场景 | 本期规则 |
| --- | --- |
| 管理端知识列表、分页、数量统计、详情 | 本人 OR 部门范围 OR 数据控制组授权范围，且始终同租户 |
| 管理端版本、FAQ 正文、审核材料、任务和切片等内容查询 | 继承所属 knowledge_item 的管理查看范围 |
| 管理端原文件下载 | 继承所属 knowledge_item 的管理查看范围，包括未发布版本 |
| 检索、问答、证据与引用 | 保持现有租户隔离及活动发布版本裁决，不增加部门条件 |
| 使用端已发布文档阅读或下载 | 不增加部门条件；仅允许活动已发布版本 |
| 写操作、后台处理、索引构建、按 knowledge_key 唯一性校验 | 维持现有租户规则，不因本期管理查看过滤隐式改变 |
| 分类、标签、问答模板等公共配置 | 不纳入知识主题归属控制，保持现状 |

不新建团队实体，不用分类代替部门，不在 Milvus 增加部门过滤，不重建向量索引，不增加 IAM 能力点门禁。管理范围条件**完全依赖 Starter** `@DataIsolation` 动态策略注入，knowledge 业务不另写策略解析器、不手工拼 OR/Other SQL。

## 2. 现状与约束

- knowledge_item 已有 create_user_id，没有创建部门字段；KnowledgeItemDao 只启用 organ_id 隔离。
- Starter 的 `@DataIsolation` 已支持 permissionTableName、userIdColumnName、deptPathColumnName；读条件可组装本人 OR 部门路径前缀 OR Other。查询与写操作均可能消费动态策略，**不能**直接改共享 DAO 注解。
- KnowledgeRetrieveServiceImpl 及写流程复用 KnowledgeItemDao 等 DAO。共享 DAO 若加部门过滤，会影响检索 MySQL 复核、写前 `selectById`、以及按 `knowledge_key` 的 `selectList` 唯一性校验。
- department 的 meta.permission_mode 决定默认部门读写位；groupRead 不代表必须加入权限组。权限组通过成员关系与 Other 规则扩展范围。
- 当前 Starter 的本人分支同时支持读写；本期不改为“本人编辑可配置”。
- **Starter 缺口（须在 P0 于 Starter 收口，不可在业务绕过）：** 当前 `policy == null`、resolve 失败、无有效分支、或主体无 deptPath 时，可能不追加范围条件而静默退回全租户。管理只读路径要求：无 meta → 仅本人；策略异常 → 明确失败；无有效分支 → 空结果；无部门用户仍可命中本人分支。上述行为做成 Starter **可选管理只读模式**，仅作用于配置了 permissionTableName 的 Mapper，不全局改变其他消费方。
- 当前隔离 SELECT 要求 from 为单表；join / EXISTS / 别名 / 分页 count 支持不足时，在 Starter 扩展，不在 knowledge 另实现。
- [DEV-003](../architecture/deviations.md) 和 AGENTS.md 目前描述“租户内全部知识接口可访问”。实施前同步更新为管理查看按团队、知识使用按租户共享；本方案不代表功能已经上线。

## 3. 数据归属

以 knowledge_item 作为唯一管理归属根。revision、chunk、task、release 等关联对象继承主题归属，不按版本创建人分别计算范围，也不复制部门字段到所有子表。

| 字段 | 处理 |
| --- | --- |
| organ_id | 保持现有受信租户字段 |
| create_user_id | 保留，创建时取可信用户上下文（管理责任人） |
| create_dept_id | 新增，可空，创建时所属部门 ID 快照 |
| create_dept_path | 新增，可空，创建时所属部门路径快照，作为 Starter 部门过滤列 |

部门 ID 和路径的物理类型、长度与 department 现有契约对齐，DDL 编写前核实，不自行假定路径上限。建议评估 (organ_id, create_user_id, delete_flag) 与 (organ_id, create_dept_path, delete_flag) 索引，通过真实 SQL 和执行计划确定最终顺序。部门字段允许为空是为了支持无部门用户，不是为兼容旧数据。

创建 knowledgeItem 时支持用户提交 createDeptId，表示本条知识的归属部门；createDeptPath 由服务端根据该部门的权威信息填写，不直接信任请求中的路径。createUserId 和 organId 始终由可信身份上下文填写。

创建接口在入库前执行以下校验：

1. 部门存在、有效、未删除，且属于当前可信 organId。
2. 当前用户确实属于该部门。可信 X-DEPT-PATH 经主体上下文解析后可用于初步校验，部门路径必须精确匹配集合中的一项，不得因具有父部门查看范围就允许将知识创建到任意下级部门。
3. 为避免 Token 中部门信息过期，在创建时通过 department 权威成员关系查询确认当前有效成员资格，并以权威部门信息保存 ID 和路径。复用现有查询契约；若不足，先补充只读契约，不使用客户端声明代替校验。
4. 提交了无效、跨租户或非本人所属部门时拒绝创建，不静默改为其他部门。校验依赖不可用时返回明确的暂不可用错误，不跳过校验；全部校验通过后才写入。

多部门用户必须明确选择一个部门，不默认取路径集合第一项。未提交部门时，若权威成员关系中仅有一个有效部门，可自动填写；存在多个有效部门则提示选择；确无有效部门时允许创建个人归属知识，部门字段为空（前端不传 createDeptId 或传空，与后端语义一致）。部门选择列表仅展示当前用户在当前租户下的有效所属部门，后端仍独立校验。

创建者或部门在普通编辑时不可修改。人员调动不自动迁移历史内容；部门树重组后由受控迁移任务核对并更新归属路径，迁移前后检查授权影响。本期不新增归属转移页面。

### 3.1 批量导入的部门归属

FAQ CSV 导入与多文件导入均纳入本需求，不允许导入路径绕过创建归属校验。

- KnowledgeImportOptionsDto 增加 createDeptId，与手动创建保持同名、同义；一次导入使用一个归属部门，导入的所有新 knowledge_item 均保存该部门 ID 与权威部门路径。
- 导入页面增加所属部门选择，候选范围、单部门默认、多部门必选、无部门个人归属规则与手动创建一致。不同部门的内容分批导入；本期不增加 CSV 行级部门列或文件级部门覆盖。
- 部门校验复用手动创建的同一领域方法，包括部门状态、租户和当前有效成员资格校验。批次选项校验在处理条目、创建主题、版本或写入源文件之前完成；选项无效或部门查询失败时拒绝整批，不产生部分导入数据。
- create_user_id 为当前导入用户，organ_id 为可信租户，不从 CSV、文件元数据或请求参数接受其他创建者和租户。create_dept_path 由服务端解析，不接受文件内容覆盖。
- 每个新主题实际创建时仍经过统一创建校验，不能仅依赖页面或批次开始时的校验。批次期间成员资格失效或部门被停用时，尚未创建的条目按既有逐条结果契约报告失败，已经成功的条目保留结果。
- 已存在 knowledge_key 沿用当前导入跳过语义，不覆盖既有部门归属。**按 key 查重必须走租户范围共享 DAO**，不得走管理只读 Mapper，以免漏判跨部门同 key。若已有条目不在当前用户管理范围内，跳过结果不得额外返回其正文、部门信息、knowledgeId 或 revisionId。
- 导入成功后，主题列表、详情及版本按保存的归属计算管理范围；submitReview 仍遵循既有审核提交流程，本期不增加写权限控制。

同步更新 FAQ 模板说明、导入接口文档、页面参数及示例，明确部门通过导入选项传递，不要求在 CSV 中填写部门名称或路径。

## 4. 查看策略

管理查询统一满足（由 Starter 注入，业务只传请求筛选）：

```text
同租户 AND 未逻辑删除 AND 请求筛选条件
AND（create_user_id = 当前用户
     OR 策略允许的部门路径范围
     OR 当前用户所属数据控制组的只读 Other 规则）
```

范围条件必须整体加括号，请求筛选只能缩小范围。分页、总数、详情、导出（如有）使用相同条件；不能先分页再在内存中过滤。

部门范围本期复用 Starter 路径前缀匹配，明确为“本部门及下级部门”。若要求仅本级部门，须另增精确匹配能力并更改验收条件，不能以当前实现声称已经支持。

本人分支始终保留。管理只读模式下降级（**Starter 实现，knowledge 不二次裁决**）：

| 情形 | 行为 |
| --- | --- |
| 无匹配 meta | 仅本人可见 |
| 策略服务异常或响应不合法 | 管理请求返回明确的暂不可用错误，不放宽至全租户 |
| 已启用策略但无有效匹配条件 | 返回空结果 |
| 主体无部门路径 | 仍可命中本人分支；不因缺 deptPath 而取消全部权限条件 |

上述行为只约束配置了管理只读模式的 Mapper，不全局改变其他 Starter 消费服务。

管理详情不可访问与不存在采用统一错误语义；下载必须在写出文件流之前完成父主题范围校验。

## 5. department 配置

使用模块实际 spring.application.name（预计 g2rain-knowledge，实施时核实）与 knowledge_item 注册模型：

1. data_permission_model：登记知识主题管理模型。
2. data_permission_field：登记 create_user_id、create_dept_id、create_dept_path 等允许配置规则的字段。
3. 为每个启用租户创建 ACTIVE meta，permission_mode=2（只读），打开默认部门查看分支。
4. 创建数据控制组，设置有效部门路径并分配成员。
5. 为 meta + group 配置只读 Other 规则，授予跨部门或指定内容范围。

例如，A 团队负责人加入协作组后，通过 Other 规则获得 B 部门知识的管理查看范围，不需要改变知识归属。组的 dept_path 必须精确命中用户可信部门路径集合，否则当前 department 解析不会命中该组。

本模型的 Other 规则统一只读，避免现有聚合方式将不同读写规则的表达式合并后扩大读范围。规则由受信管理入口按字段白名单生成和校验，不接受知识管理普通用户提交任意 SQL。

本期“分组”指对已有归属数据配置查看范围，不给每条知识新增 group_id 或多组归属关系。权限与成员变更复用现有缓存失效广播与 TTL；联调记录实际生效窗口并写入验收记录。

## 6. 实现结构

### 6.1 查询边界（完全依赖 Starter）

保留现有通用 DAO 的**仅租户**隔离语义，供写流程、处理任务、按 key 查重与共享使用路径调用。新增专用管理只读 Mapper（建议 KnowledgeItemManagementQueryDao），只暴露查询，配置：

```text
permissionTableName = knowledge_item（或登记名）
userIdColumnName = create_user_id
deptPathColumnName = create_dept_path
并启用 Starter 管理只读模式（fail-closed / 无 meta 仅本人）
```

管理 Service 只负责将管理入口路由到该 Mapper，**不**预查策略、不拼权限 SQL。关联对象先经父主题管理查询授权；跨主题版本、任务列表及其统计用联表或 EXISTS 在 SQL 内限制父主题范围，不允许先取全量再过滤。join / 别名 / EXISTS / 分页 count 由 Starter 支持；不足则先扩展 Starter，再写业务。

### 6.2 写路径与 key 查重隔离

现有 save/delete/review/publish 等调用不得改为使用管理只读 Mapper。写前预查清单至少包括：

| 预查类型 | 典型调用 | 路径 |
| --- | --- | --- |
| 按 id | `selectById`（item / revision / task / …） | 共享租户 DAO |
| 按 knowledge_key | `selectList(knowledgeKey)` 唯一性、导入 skip | 共享租户 DAO（全租户内判重） |

逐一核对后证明：新增管理查看范围没有间接改变写权限或 key 唯一性语义。本期不通过“页面隐藏按钮”宣称已具备跨团队写保护（产品上也不要求该保护）。

### 6.3 使用路径与下载

检索和问答仍使用租户范围查询，并保留 MySQL 活动 revision 裁决。引用只返回现有契约允许的已发布证据。既有内部校验不得为实现共享而删除。

**下载（P0 硬决策，二选一）：**

1. P0 列出 App 全部 download 调用方后，若存在使用端依赖：拆出独立的已发布资源读取入口（服务端解析活动版本），现有 `GET /knowledge_revision/{revisionId}/source/download` 定位为管理材料下载并纳入管理范围；或  
2. 书面确认无使用端文档下载后，直接将现有入口纳入管理范围，本期不新建使用端入口。

禁止用客户端传入 management=false 等开关绕过管理权限。

### 6.4 前端

知识管理页面默认展示授权范围，可提供“我创建的”“部门范围”快捷筛选，筛选只收窄结果。**“部门范围”快捷筛选不得取消本人 OR**：即仍包含当前用户创建的内容（含归属已不在所选部门树下的本人历史），避免用户误判为权限丢失。

新建与导入页提供所属部门选择并提交 createDeptId；单部门可默认选中，多部门要求明确选择，无部门时不传或传空。详情展示创建者和所属部门的只读信息；无法访问时清理旧详情和缓存，不继续显示上次响应的正文。

管理页面的数据缓存必须区分用户与租户，并在切换身份、部门后失效。使用端检索、问答、引用交互保持现状。控制组配置复用 department 管理入口，不在 knowledge 内复制配置体系。

1. 直接修改标准建库 DDL、接口契约及初始化数据；为已有开发库提供一次性结构更新脚本，不提供旧版本兼容模式。
2. 按生成器约束生成并审阅 PO/DTO/VO/Mapper 差异，避免覆盖既有领域逻辑；所有调用方直接切换目标契约。
3. 更新开发和测试数据，为验收样例显式设置创建者、部门及控制组；本期不建设生产历史数据回填、待认领或迁移审计流程。
4. 如需重建开发库，仅针对明确指定且获准清理的测试数据执行，不因本方案自动删除现有数据。
5. 表结构、策略初始化、Starter、后端与前端作为同一开发变更集完成联调；不设计双写、逐租户灰度、旧契约回退或关闭权限过滤的兼容开关。

## 9. 验收标准

- A 部门用户看到本人、A 部门及下级范围；看不到未授权 B 部门管理内容。本人创建内容即使归属旧部门仍可查看；前端“部门范围”筛选后本人内容仍可见。
- 加入有效控制组后可查看指定 B 部门范围；撤销授权后在联调记录的缓存窗口内失效。
- 多部门成员按可信路径集合计算；同级路径不串组，无部门用户只命中本人或有效例外规则。
- 列表、分页总数、详情、子资源列表及管理下载一致；直接猜版本、任务、切片 ID 无法绕过父主题管理范围。
- A 部门用户仍可检索和引用 B 部门的活动已发布知识；不得因此获取草稿、下线或非活动版本。
- 其他租户数据在所有入口始终不可见，Other 规则不能突破 organ_id。
- 无 meta 仅本人；策略异常明确失败；无有效分支为空；无 deptPath 不退回全租户；前端筛选、别名和 OR 条件不能放宽范围。上述行为由 Starter 管理只读模式保证，业务无旁路实现。
- 通过直接调用既有写接口验证本期未新增写权限限制；按 knowledge_key 查重仍覆盖租户内全部主题；后台处理、审核、发布流程不因管理查询拆分而失效。
- 合法所属部门可创建；不存在、停用、已删除、跨租户、非成员部门及仅有父路径前缀匹配的部门均不能作为创建归属；过期 Token 的旧成员资格不能绕过权威查询；依赖异常不落库。
- 单部门省略时自动补齐，多部门省略时提示选择，无部门时允许个人归属；客户端伪造创建者或部门路径不生效；普通更新不改变归属；建库和初始化脚本可直接构建目标模型。
- FAQ CSV 和多文件导入均可提交 createDeptId，全部新主题的部门归属与选择一致；非法批次部门在产生副作用前整批拒绝，条目创建时复用同一校验；重复键不覆盖归属或泄露不可管理内容。
- 使用真实 MySQL 验证 SQL 过滤、分页计数、逻辑删除、索引与活动版本复核；运行 mvn clean verify，前端执行项目规定的构建与检查。方案阶段不声称测试通过。
